Domain Introduction: Design Determines Security Outcomes

Welcome to Domain 3: Security Architecture and Engineering. This domain transitions from policy definition (Domain 1) and data labeling (Domain 2) to the technical core of systems engineering. The central thesis of Domain 3 is simple: architectural design choices determine security outcomes. Adding security products to a poorly designed architecture is a costly and ineffective strategy.

Accounting for 13% of the overall CISSP CAT exam, Domain 3 is highly technical. It covers hardware security, operating system memory protections, formal security models, platform vulnerabilities, cryptography, and facility security. It is the broadest technical domain in the Common Body of Knowledge (CBK).

🧠 Think Like a Manager
When evaluating security architecture, remember that design simplicity is a key control. A manager prioritizes standard secure design patterns over complex configurations that are prone to user error and configuration issues.

Our focus in this session is to explore the underlying architectural principles that make systems resilient, examine the formal models that govern access control, and analyze how cryptographic structures protect modern data processing.

Foundational Secure Design Principles

Secure design principles are structural design rules that minimize system attack surface and limit the blast radius of potential compromises. These principles are technology-neutral and apply across all computing environments.

1. Least Privilege

This principle ensures that every user, service account, and process is granted only the minimum necessary permissions to perform their designated tasks. Minimizing access limits lateral movement if an account is compromised. *Example violation: A standard web server process running under an administrator/root account instead of a restricted, dedicated service account.*

2. Defense in Depth (Layered Security)

Implementing multiple independent security controls across administrative, physical, and technical layers. It assumes that any single control can fail. *Example: Perimeter firewall + host-based endpoint protection + encrypted database files.* Implementing identical firewalls from the same vendor does not constitute defense in depth; true resilience relies on control diversity.

3. Secure by Default

Systems should ship with their most secure settings enabled. Unused ports should be closed, default passwords disabled, and optional services turned off out of the box. Administrators must explicitly opt-in to enable features rather than opting-out to disable vulnerabilities.

4. Fail Safe / Fail Secure vs. Fail Open

When system components crash, they must default to a state that maintains security:

  • Fail Safe: Prioritizes human life and safety. If a fire alarm triggers, physical security doors must unlock automatically (fail open for evacuation) to protect occupants.
  • Fail Secure: Prioritizes asset protection. If a software firewall crashes, the network interface must block all incoming traffic (fail closed) to prevent unauthorized access.
🎯 Exam Tip
In CISSP exam scenarios, human safety always takes precedence over asset protection. If a facility fire alarm triggers, access control doors must fail-safe (unlocking the doors to allow escape), even if this compromises the physical security of sensitive server racks.

5. Complete Mediation

Every access request to every object must be validated against an authorization matrix. This validation cannot be bypassed, cached, or bypassed for convenience. Complete mediation is a core requirement of Zero Trust architectures.

6. Economy of Mechanism

Keep designs as simple as possible. Complexity increases the risk of software bugs, administrative misconfigurations, and overlooked vulnerabilities. Simple systems are easier to configure, audit, and maintain.

7. Open Design

System security must rely on the strength of encryption keys and passwords, not on keeping the system's design secret. Open algorithms (such as AES) undergo rigorous peer review, whereas "security through obscurity" is prone to exploitation.

Secure Design Principles Matrix

Principle Core Objective Design Application Common Violation
Least Privilege Restrict access surface Configure narrow service account access rights. Using root/admin credentials for basic application services.
Defense in Depth Prevent single point of failure Layer firewalls, network segmenting, and FDE encryption. Relying entirely on a perimeter firewall to protect databases.
Economy of Mechanism Reduce design complexity Use modular code and standard, clean interfaces. Adding custom, untested integrations that inflate code.

Formal Security Models

Formal security models translate high-level security policies into structured, mathematical rules that govern how software and operating systems must enforce access control.

1. Bell-LaPadula Model (Confidentiality)

Developed for the US Department of Defense, Bell-LaPadula is a state-transition model designed to protect confidentiality and prevent unauthorized disclosure of information.

  • Simple Security Property (No Read Up): A subject cannot read data at a higher classification level than their current clearance.
  • Star (*) Property (No Write Down): A subject cannot write data to a lower classification level. This prevents users with high clearances from leaking classified information into lower-security files.

Key Limitation: It does not protect data integrity; it only prevents unauthorized disclosure.

2. Biba Model (Integrity)

The mathematical inverse of Bell-LaPadula, the Biba model is designed to protect data integrity and prevent unauthorized modifications.

  • Simple Integrity Property (No Read Down): A subject cannot read data from a lower integrity level to prevent contaminating high-integrity processes with untrusted data.
  • Star (*) Integrity Property (No Write Up): A subject cannot write data to a higher integrity level. This prevents low-integrity entities from modifying or corrupting high-integrity files.

Key Limitation: It does not protect confidentiality.

🎯 Exam Tip
Remember the properties using this quick guide: Bell-LaPadula is about confidentiality (preventing unauthorized reading, so "No Read Up / No Write Down"). Biba is about integrity (preventing data corruption, so "No Read Down / No Write Up").

3. Clark-Wilson Model (Commercial Integrity)

Designed for commercial organizations, Clark-Wilson enforces integrity using well-formed transactions and separation of duties. Users cannot modify data directly; instead, they must use authorized programs called Transformation Procedures (TPs).

The model uses the following components:

  • Constrained Data Items (CDIs): Core databases and datasets whose integrity must be preserved.
  • Unconstrained Data Items (UDIs): Raw input data from external sources that has not yet been validated.
  • Transformation Procedures (TPs): The only application programs authorized to modify CDIs. They validate input and ensure data remains in a consistent state.
  • Integrity Verification Procedures (IVPs): Auditing processes that run independently to verify that CDIs conform to integrity policies.

4. Brewer-Nash Model (Chinese Wall)

The Brewer-Nash model dynamically restricts access based on a user's access history to prevent conflicts of interest. Once an analyst accesses data from one competitive organization, the model automatically blocks them from accessing data from competing organizations. This model is commonly used in consulting, auditing, and law firms.

System Security Capabilities

System security capabilities are the hardware, firmware, and operating system-level mechanisms that provide the foundation for all higher-level security controls.

1. The Trusted Computing Base (TCB)

The TCB encompasses all hardware, firmware, and software components that are critical to enforcing a system's security policy. A vulnerability in any TCB component can compromise the security of the entire system. To ensure trustworthiness, the TCB should be kept as small as possible to simplify auditing and validation.

2. The Reference Monitor and Security Kernel

  • Reference Monitor: A conceptual model of the enforcement mechanism that mediates all access between subjects and objects. It must be: always invoked (complete mediation), tamper-resistant, and small enough to be verified (economy of mechanism).
  • Security Kernel: The hardware, firmware, and software implementation of the reference monitor concept.

3. Trusted Platform Module (TPM)

The TPM is a dedicated hardware cryptographic chip soldered onto system motherboards. It provides secure key generation, secure storage for encryption keys, platform integrity measurements, and measured boot capabilities. Because cryptographic keys are stored in hardware, they are protected from extraction by software-only attacks.

4. Operating System Memory Protection

Prevents processes from accessing memory spaces allocated to the OS kernel or other active tasks:

  • DEP/NX (Data Execution Prevention / No-Execute): Marks specific memory regions (such as the stack) as non-executable. This prevents attackers from executing injected shellcode via buffer overflow attacks.
  • ASLR (Address Space Layout Randomization): Randomizes memory locations of system processes and components. This makes it difficult for exploits to predict the target memory addresses of specific functions.

5. Virtualization Security (Hypervisors)

Virtualization isolates guest operating systems on shared physical hardware using a hypervisor:

  • Type 1 (Bare-Metal) Hypervisors: Run directly on physical hardware (e.g., VMware ESXi, Hyper-V). This approach is highly secure and is standard in enterprise data centers.
  • Type 2 (Hosted) Hypervisors: Run as software applications on top of a host operating system. They are less secure due to the increased attack surface of the underlying host OS.
  • VM Escape Risk: An attack vector where a process inside a virtual machine bypasses hypervisor boundaries to access the host operating system or other virtual machines. Securing the hypervisor is critical.

Platform Vulnerabilities and Mitigations

Security architectures must address specific threats across diverse computing environments. Security controls should be tailored to the unique risks of each platform.

1. Web Application Flaws (The OWASP Top 10)

Web applications are highly exposed to public-facing attacks. Common vulnerabilities include:

  • Injection (SQLi, XSS): Attackers submit malicious code that is interpreted and executed by the backend database or user browsers. *Mitigation: Rigorous input validation, output encoding, and parameterized queries.*
  • Broken Access Control: Users bypass access control checks to view or modify unauthorized files. *Mitigation: Complete mediation checks on every server-side request.*

2. Industrial Control Systems (SCADA / ICS)

SCADA and ICS platforms manage physical processes in critical infrastructure (such as electrical grids, water treatment plants, and assembly lines). In these environments, **availability and safety always outrank confidentiality**.

Many ICS devices use legacy protocols (such as Modbus or DNP3) that lack native authentication or encryption. Because patching can cause downtime or safety risks, organizations must implement compensating controls: isolating ICS networks using the **Purdue Model**, enforcing strict network segmentation, and deploying unidirectional data diodes.

⚠️ Watch Out
Historically, SCADA environments relied on physical isolation (the "air gap") for security. This assumption is no longer valid. Modern attacks (such as Stuxnet) have demonstrated that malware can bridge air gaps via USB media. Defensive designs must assume the network is accessible.

3. Embedded Devices and the Internet of Things (IoT)

Embedded systems and IoT devices often lack the CPU power, memory, and battery capacity to run standard security software or full encryption stacks. They frequently ship with hardcoded default credentials and lack secure remote patching mechanisms. Mitigations include segmenting IoT devices into isolated VLANs, requiring signed firmware updates, and implementing secure boot protocols.

4. Cloud Architecture Vulnerabilities

The cloud relies on the **Shared Responsibility Model**. The cloud provider secures the underlying physical infrastructure, while the customer is responsible for configuring access policies, securing data, and managing applications.

Misconfigurations (such as leaving S3 buckets publicly accessible) are the leading cause of cloud data breaches. Mitigations include deploying Cloud Security Posture Management (CSPM) tools and enforcing strict Identity and Access Management (IAM) policies.

Cryptography Fundamentals

Cryptography is a critical technical control for protecting data confidentiality, integrity, and authenticity. Security managers must understand algorithm behaviors, key lengths, and operational tradeoffs.

1. Symmetric vs. Asymmetric Cryptography

Modern encryption relies on two primary cryptographic methods:

  • Symmetric Encryption (Shared Key): Uses a single, identical key for both encryption and decryption. Symmetric encryption is highly performant and suitable for bulk data encryption. *Algorithms: AES (current standard), 3DES (deprecated), DES (broken).*
  • Asymmetric Encryption (Public/Private Key): Uses a mathematically linked key pair. Data encrypted with the public key can only be decrypted by the private key. Asymmetric encryption is computationally intensive and is primarily used for key exchange and digital signatures. *Algorithms: RSA, ECC (Elliptic Curve Cryptography).*

2. Cryptographic Hashing and Passwords

A hash function takes variable-length input and generates a unique, fixed-length string (digest). Hashing is a one-way mathematical function that cannot be reversed. *Algorithms: SHA-256, SHA-3 (secure); MD5, SHA-1 (broken/deprecated).*

Password hashing requires special algorithms (such as **bcrypt, scrypt, or Argon2**) that are designed to be slow and computationally expensive. This design slows down brute-force and dictionary attacks. Additionally, a unique random value (a **salt**) must be added to each password before hashing to protect against precomputed rainbow table attacks.

3. Digital Signatures and Nonrepudiation

A digital signature is created by hashing a message and encrypting that hash with the sender's private key. The recipient decrypts the signature using the sender's public key and compares it to a fresh hash of the received message.

Digital signatures provide three key properties:

  • Authenticity: Proves that the message was sent by the owner of the private key.
  • Integrity: Verifies that the message was not modified in transit.
  • Nonrepudiation: Prevents the sender from denying the transaction, as only they possess the private key used to create the signature.

4. Public Key Infrastructure (PKI)

PKI is the framework of hardware, software, people, and policies used to manage digital certificates. The CA (Certificate Authority) acts as the trust anchor by digitally signing end-entity certificates. Real-time certificate validation is managed using CRLs (Certificate Revocation Lists) or OCSP (Online Certificate Status Protocol) queries.

Advanced Cryptography & Cryptanalytic Attacks

Even strong cryptographic algorithms can be bypassed if they are implemented poorly, use weak key management, or use outdated protocols.

1. Common Cryptanalytic Attacks

  • Brute Force: Attempting every possible key combination until the correct one is found. This is mitigated by using longer key lengths (e.g., AES-256).
  • Birthday Attack: Exploits the birthday paradox (statistical probability of matches) to find hash collisions, where two different inputs produce the same hash output. High-output hash lengths (such as SHA-256) resist this attack.
  • Known Plaintext Attack (KPA): The attacker has access to both a plaintext message and its corresponding ciphertext. They attempt to derive the key from this relationship.
  • Chosen Plaintext Attack (CPA): The attacker selects plaintext inputs and observes the resulting ciphertexts. Algorithms that produce identical ciphertext for identical input (such as AES in Electronic Codebook - ECB mode) are highly vulnerable.
  • Side-Channel Attack: Targets the physical characteristics of encryption execution rather than the mathematical algorithm. It measures timing variations, power consumption patterns, or electromagnetic emissions to leak cryptographic keys.

2. Quantum Computing and Cryptography

The development of quantum computers poses a significant future risk to modern cryptography:

  • Shor's Algorithm: A quantum algorithm that can efficiently solve the prime factorization problems behind RSA and ECC encryption. A sufficiently powerful quantum computer could break current asymmetric encryption systems.
  • Grover's Algorithm: Reduces the effective strength of symmetric keys (e.g., AES-128 becomes equivalent to AES-64). Mitigate this risk by upgrading to 256-bit symmetric keys (AES-256), which provide sufficient quantum resistance.
  • Post-Quantum Cryptography (PQC): The development of new algorithms that are resistant to quantum computing attacks. NIST finalized its first set of PQC standards (including ML-KEM and ML-DSA) in 2024.
💡 Pro Tip: Crypto Agility
Cryptographic Agility is the architectural ability to quickly update or replace cryptographic algorithms across an enterprise without requiring major software re-engineering. This is a critical design requirement for transitioning to post-quantum security baselines.

Physical and Facility Security

Physical security is the foundational layer of any security program. If an attacker gains unauthorized physical access to a system, they can often bypass logical and software-based security controls.

1. Layered Physical Defense (Defense in Depth)

Physical security should be designed using concentric layers of defense, moving from the outer perimeter to the core assets:

Layered Facility Access Mapping

Layer 1: Perimeter (Fences, bollards, security lights, CCTV)
Layer 2: Facility Shell (Reception desk, visitor logs, mantraps)
Layer 3: Secure Rooms (Server rooms, wiring closets, biometric locks)
Layer 4: Asset Level (Server racks, physical cage enclosures, port locks)

2. Access Control Vestibules (Mantraps)

A mantrap is a secure enclosure containing two interlocking doors. One door must close and lock before the second door can open. This prevents tailgating or piggybacking, where unauthorized individuals follow an authorized employee through a secure doorway.

3. Environmental Controls (HVAC)

HVAC systems must maintain stable temperature and humidity levels to prevent hardware failures:

  • Temperature Intake: Standard guidelines recommend intake temperatures between 64°F and 80°F (18°C to 27°C).
  • Humidity Levels: Relative humidity must be maintained between 40% and 55%. High humidity can lead to water condensation and short circuits; low humidity increases the risk of static electricity discharges.

4. Power Protection: UPS and Generators

Data centers require reliable power to maintain availability. If utility power fails, an **Uninterruptible Power Supply (UPS)** battery backup provides immediate, clean power to bridge the gap (typically 10 to 30 seconds) until diesel generators start up and stabilize.

5. Fire Suppression Classifications

Fire Class Fuel Source Recommended Suppression Agent Never Use
Class A Ordinary combustibles (paper, wood, trash) Water, dry chemical agents. —
Class B Flammable liquids (gasoline, oil, solvents) CO2, foam, gaseous clean agents. Water (spreads liquid fire).
Class C Electrical equipment (servers, switches, wiring) FM-200, Novec 1230, gaseous clean agents. Water (electrical shock & equipment damage).
Class K Commercial kitchen fires (fats, cooking oils) Wet chemical agents. Standard water or dry chemicals.
⚠️ Watch Out
**Halon gaseous fire suppression systems are banned** due to ozone depletion regulations. For modern data centers, clean agent systems like **FM-200 or Novec 1230** are the standard. They suppress fires without damaging delicate electronics or leaving conductive residue.

Security Control Selection & Architecture Analysis

Security control selection is the process of choosing technical, administrative, and physical controls to mitigate identified risks. These controls are selected based on security requirements, budget constraints, and risk tolerance.

1. Security Control Categories and Functions

Controls are classified into three primary categories and several functional types:

  • Categories:
    • Administrative: Policies, procedures, training, and personnel background checks.
    • Technical (Logical): Access controls, firewalls, encryption, and IDSs.
    • Physical: Fences, security guards, door locks, and water sensors.
  • Functions:
    • Preventive: Stop security incidents before they occur (e.g., firewalls, locks, encryption).
    • Detective: Identify incidents in progress or after they occur (e.g., IDS, CCTV, system logs).
    • Corrective: Restore normal operations after an incident (e.g., restoring backups, patching).
    • Compensating: Alternative controls implemented when primary controls are not feasible (e.g., using isolation for an unpatchable server).

2. Trust Boundary Analysis

A trust boundary is any logical or physical perimeter in a system design where data transitions from one security level to another. Each trust boundary is an attack vector and must be secured.

When analyzing architectures, security teams must map data flows across these boundaries. For example, when public user traffic transitions from the Internet to a DMZ, the boundary must be protected by a Web Application Firewall (WAF) and input validation controls.

💡 Pro Tip: Zero Trust Architecture
Traditional network architectures assumed security was defined by perimeter boundaries. **Zero Trust** removes this assumption. It treats every user, device, and network segment as untrusted, requiring continuous verification and authentication at every transition point.

Domain 3 Scenario Practice

Applying Domain 3 concepts on the exam requires analyzing scenarios from an architectural perspective. Avoid jumping directly to product solutions; instead, start by analyzing the underlying design principles and trust boundaries.

Scenario 1 — Parameterized Queries and Input Validation

The Situation: A developer is building a public web portal for a medical insurance system. The system must query customer record databases based on user-submitted search parameters. A security review reveals SQL injection vulnerabilities.

The Architectural Response: The primary issue is a lack of input validation and complete mediation at the application trust boundary. To mitigate this risk, the developer must implement **parameterized queries** (prepared statements) within the code. This ensures that user inputs are treated strictly as data parameters rather than executable commands, neutralizing SQL injection vectors.

Scenario 2 — Classifying Federal Intelligence Records

The Situation: A military contractor is building a document classification system. Users with "Secret" clearances need to read historical field logs but are prohibited from writing updates into "Unclassified" shared folders.

The Architectural Response: This scenario requires enforcing confidentiality within a classified environment, making the **Bell-LaPadula** model the appropriate choice. The system must enforce the *Simple Security Property* (blocking users from reading documents above their clearance, or No Read Up) and the *Star Property* (blocking users from writing classified data into lower-classification folders, or No Write Down).

Scenario 3 — Securing Legacy SCADA Network Boundaries

The Situation: An energy provider operates a hydroelectric power plant managed by legacy PLCs running outdated firmware. Patching the systems is not feasible because the vendor has gone out of business, and downtime could threaten regional power stability.

The Architectural Response: This scenario requires prioritize availability and safety over confidentiality, making standard IT patching impractical. The security team must implement **compensating controls**: isolating the SCADA network using **VLAN segmentation** (per the Purdue Model), blocking inbound Internet access to the PLC subnets, and deploying **unidirectional data diodes** to export operational logs without permitting incoming control commands.

Scenario 4 — Designing physical access controls for a financial data vault

The Situation: A financial institution is building a secure physical vault to store hard drives containing encryption keys. The team needs to prevent tailgating and secure the facility from unauthorized physical entries.

The Architectural Response: To secure high-value physical assets, the team must implement a layered physical defense. Key controls include deploying a **biometric mantrap (access control vestibule)** at the entry to prevent tailgating, installing photoelectric smoke detectors with clean agent gaseous suppression (FM-200), and maintaining an independent battery-powered biometric access log.

Domain 3 Summary: Security Architecture & Engineering

Domain 3 provides the core engineering and design principles required to build secure, resilient systems. By applying secure design principles like least privilege and defense in depth, organizations can minimize attack surfaces and mitigate potential compromises. Implementing formal security models (such as Bell-LaPadula and Biba) helps translate access policies into system rules. Additionally, cryptographic controls protect data confidentiality and integrity, while robust physical and environmental protections secure the underlying hardware infrastructure. To succeed on the exam, prioritize structural secure design patterns and understand that safety and availability must always outrank confidentiality in operational technology (OT) and critical infrastructure environments.

🎯 3 Key Exam Reminders

  • Human Safety Outranks All: In physical security scenarios, human safety always outranks asset protection. During fire alarms or emergency evacuations, access control doors must fail-safe (unlocking automatically to allow escape).
  • Model Enforcements: Remember the properties of the core security models: Bell-LaPadula protects confidentiality (no read up, no write down), whereas Biba protects integrity (no read down, no write up).
  • Class C Fire Suppression: Never use water on Class C electrical fires. Gaseous clean agents (such as FM-200 or Novec 1230) are the industry standard for suppressing fire in sensitive electronics environments.
