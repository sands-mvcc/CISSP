Software Development Security

Building security into software — not bolting it on after the fact

⏱ 2.5 Hours Study 📋 10 Core Topics 🎯 10% Exam Weight 📅 Day 5 Morning

Learning Objectives

By the end of this lesson, you will be able to:

  • Integrate security requirements, controls, and testing into each phase of the SDLC from requirements through maintenance.
  • Compare development methodologies—Waterfall, Agile, Spiral, DevOps, and DevSecOps—and identify security touchpoints.
  • Apply secure design principles and threat modeling to identify attack surfaces and architectural risks before code is written.
  • Apply secure coding practices—including input validation, output encoding, error handling, and secrets management.
  • Select and apply testing methods (SAST, DAST, IAST, fuzzing, code reviews) and analyze their detection capabilities.
  • Identify and mitigate common application and database vulnerabilities like SQL injection, XSS, CSRF, and buffer overflows.
  • Apply database security controls including access control, transaction integrity (ACID), and input validation.
  • Implement secure build and deployment practices—including version control, pipeline security, and container security.
  • Assess and manage software supply chain risk, third-party libraries, open-source risk, and SBOM requirements.
  • Apply software maintenance security practices—including logging, secure update channels, and end-of-life planning.

Core Lesson Content

Domain Introduction: Software is the Attack Surface

Welcome to Domain 8: Software Development Security. This domain covers 10% of the overall CISSP exam. The core thesis of Domain 8 is simple: software is the attack surface. The vast majority of modern network and data compromises ultimately succeed by exploiting an application-layer or database vulnerability.

Building secure software is a fundamental risk-management requirement. When development teams fail to address security as an upfront design requirement, organizations are forced to rely on reactive network controls. CISSP candidates must view software through a governance lens, ensuring that secure design patterns, automated testing, and supply chain controls are built directly into the lifecycle.

🧠 Think Like a Manager
A security manager views software through the lens of early risk reduction. Integrating security checks early in the lifecycle ("shifting left") is highly cost-effective: a vulnerability fixed during design costs up to 100 times less than remediating the same vulnerability after release in production.

We will examine the essential components of software security, ranging from threat modeling and the OWASP Top 10 to dependency checking, build pipeline security, and container hardening.

Integrating Security into SDLC Methodologies

Modern software development is governed by formal lifecycles. Integrating security requires understanding how security touchpoints map to different development models.

SDLC Phases and Security Touchpoints

  • Requirements gathering: Define confidentiality, integrity, availability, and compliance requirements. Draft abuse/misuse cases.
  • Design phase: Conduct threat modeling (STRIDE) and establish secure architecture patterns (such as encryption standards and central access gates).
  • Development phase: Use secure coding standards, integrate SAST scanners into development environments, and enforce secrets management.
  • Testing phase: Run DAST, IAST, fuzzing, and manual application-layer penetration tests.
  • Deployment phase: Validate artifact signatures, hard container runtimes, and configure deployment secrets.
  • Maintenance: Monitor for vulnerabilities, apply patches, and coordinate secure update channels.

💡 Pro Tip: The Security Champion Model
To scale security in fast Agile or DevSecOps teams, deploy Security Champions. These are designated software developers who receive specialized security training. They advocate for security within their teams, run code reviews, and coordinate with the centralized security department.

Secure Requirements, Design, and Threat Modeling

Security is determined during design. Building secure requirements and evaluating threats before writing code is the highest-leverage practice in software development.

Abuse Cases vs. Misuse Cases

  • Abuse Case: Describes how an adversary might maliciously abuse a legitimate application function. Example: An attacker using a forgot-password password reset page to harvest valid usernames.
  • Misuse Case: Explores how an attacker might intentionally exploit a design flaw or vulnerability to bypass security boundaries. Example: Injecting SQL commands into a search field to bypass database access controls.

STRIDE (developed by Microsoft) is an industry-standard framework used to systematically analyze system data flow diagrams (DFDs) and identify threats during system design:

⚠️ Watch Out
Threat modeling is not a point-in-time task. It must be updated whenever significant modifications are introduced to application architectures, new APIs are integrated, or trust boundaries are crossed.

Secure Coding Best Practices

Secure coding practices neutralize standard vulnerability classes at the implementation level. Secure code design requires assuming that all external inputs are potentially malicious.

1. Server-Side Input Validation

All data received from untrusted sources (including browsers, API clients, cookies, and database tables) must undergo validation. Client-side validation (using JavaScript) is not a security control. It can be easily bypassed using local intercepting proxies. All security-significant validation must be executed on the server.

Prefer allowlist validation (defining exact patterns of acceptable input and rejecting everything else) over denylist validation (blocking known malicious characters), which is prone to bypasses.

2. Output Encoding

To prevent browser-based script execution or database interpretation, untrusted data must undergo context-specific output encoding before being rendered to users. Converting characters to their safe equivalents (such as &lt; and &gt; for < and >) prevents malicious scripts from executing.

3. Memory Safety and Buffer Overflows

Buffer overflows occur when an application writes more data to a memory buffer than it is allocated to hold, overwriting adjacent stack memory and redirecting execution flow.

While using memory-safe languages (like Python, Java, or Rust) prevents these issues automatically, legacy systems written in C or C++ require strict defenses: validating string lengths before write operations, using safe library functions (like strncpy instead of strcpy), and compiling with stack canaries, ASLR, and DEP/NX memory protections.

💡 Secrets Management Rule
Never hardcode credentials in source code. Passwords, connection strings, API keys, and certificates must be isolated from repository source files and injected dynamically at runtime using dedicated systems like HashiCorp Vault or AWS Secrets Manager.

Software Security Testing Methodologies

Validating application security requires matching testing methodologies to the characteristics of the target software. No single testing method is sufficient on its own.

Fuzz Testing and Code Reviews

  • Fuzzing: Automated testing that inputs malformed, random, or boundary-bursting data into application entry points to identify memory leaks, unhandled exceptions, and system crashes.
  • Manual Code Review: A thorough review of source code by security specialists to identify complex logical flaws, authorization bypasses, and secure coding violations that automated scanners miss.
🎯 Exam Tip
When asked how to validate the security of third-party software for which no source code is available, the correct answer is to use DAST and dynamic application penetration testing, as SAST requires access to raw source files.

Common Application & Database Vulnerabilities

Security teams must understand how core application and database exploits operate and implement appropriate countermeasures to neutralize them.

1. SQL Injection (SQLi)

SQLi occurs when user input is concatenated directly into a SQL statement, allowing the database interpreter to execute malicious SQL command parameters. Remediation: Mandate the use of Parameterized Queries (Prepared Statements). Parameterization separates executable code from input parameters, ensuring that the database engine treats input strictly as data, never as executable code.

2. Cross-Site Scripting (XSS)

XSS allows an attacker to inject malicious client-side script into web pages viewed by other users. Remediation: Implement context-aware output encoding, configure a strong Content Security Policy (CSP) header to restrict script execution, and apply the HttpOnly cookie flag to protect session cookies.

3. Cross-Site Request Forgery (CSRF)

CSRF forces an authenticated browser to submit unauthorized requests to a trusted application on behalf of the user. Remediation: Implement unpredictable, session-bound CSRF tokens that the application validates on every state-changing POST request, and configure the SameSite cookie attribute to restrict cross-site submissions.

4. Database Transaction Integrity (ACID)

Database transaction engines rely on ACID properties to prevent data corruption and race conditions:

  • Atomicity: Ensures that all operations within a transaction complete successfully, or the entire transaction is rolled back. No partial updates are permitted.
  • Consistency: Guarantees that database transactions bring the database from one valid state to another, enforcing all integrity rules.
  • Isolation: Ensures that concurrent transactions execute independently as if they were sequential, preventing concurrency-related race conditions.
  • Durability: Guarantees that once a transaction is committed, its state persists in non-volatile storage even during system crashes.

Secure Build and Deployment Pipeline Design

Software security extends beyond application code. Securing the build pipeline, repository access, and container packaging is critical for preventing supply chain compromises.

1. Repository and Version Control Security

Version control repositories house an organization's intellectual property. To secure them, enforce branch protection rules that require code review and build approvals before code is merged into production branches. Additionally, deploy automated scanners to detect and block committed secrets (such as API keys) before they enter repository histories.

2. Hardening Build Pipelines (CI/CD)

The build pipeline is a highly valuable target. Securing it requires: isolating build environments using ephemeral, short-lived container instances, and signing compiled artifacts cryptographically to detect tampering between the build and deployment phases.

3. Container Hardening and Image Registry Security

When deploying containerized applications, organizations must harden container environments:

  • Minimal Base Images: Use minimal base images (such as Alpine or distroless images) to minimize the attack surface by excluding unnecessary shells and package managers.
  • Privileged Processes: Run container processes as non-root users. This prevents attackers from escalating to host-level administrative privileges if they break container boundaries.
  • Image Scanning: Scan container images in the registry automatically for known vulnerabilities (CVEs) before they are deployed to production clusters.

Software Supply Chain Security

Modern applications are rarely built entirely from scratch; they often rely on extensive networks of open-source libraries and third-party dependencies that must be continuously evaluated.

The Software Bill of Materials (SBOM)

An SBOM is a machine-readable, structured inventory of all software components, library versions, and licenses embedded within an application. SBOMs (formatted in standard CycloneDX or SPDX formats) are critical for rapid incident response. For example, during wide-scale vulnerability disclosures like Log4Shell, organizations can query their SBOM database to identify and patch affected applications within seconds.

Software Composition Analysis (SCA)

SCA tools automate the process of scanning an application's direct and transitive dependencies against updated vulnerability databases (such as the NVD). SCA scanners should be integrated into build pipelines to block deployments if high-severity vulnerabilities are detected in imported packages.

Dependency Pinning and registries

To defend against typosquatting and dependency confusion attacks, organizations should implement private registries that cache and scan public packages. Additionally, developers should use Dependency Pinning to lock direct packages to specific cryptographic hashes, preventing build systems from pulling unvetted upstream updates automatically.

Operational Software Maintenance and End-of-Life

Software security is an ongoing lifecycle. Deployed applications require continuous operational monitoring, patch management, and end-of-life planning.

1. Operational Application Security Logging

Applications must log security-significant events (such as failed authentication attempts, privilege changes, and access denials). However, sensitive user data (like passwords, credit card numbers, or session tokens) must never be written to logs. A log entry for a failed login should record the username and timestamp—never the password that was attempted.

2. Secure Update Channels

Update delivery mechanisms must enforce cryptographic verification. The updater must sign update packages with their private key, and the recipient must verify this signature using the vendor's public key before applying the update, preventing man-in-the-middle software updates.

3. End-of-Support (EOS) Risk Management

When software reaches its End-of-Support (EOS) date, the vendor stops releasing patches and security fixes. Operating unsupported legacy software introduces significant risk. Organizations must proactively retire these platforms or implement compensating controls (such as strict network isolation or enhanced host monitoring) if the systems must remain active.

Domain 8 Scenario Practice

Domain 8 exam questions are scenario-based architecture and development problems. To choose the correct answer, you must analyze these scenarios from a governance perspective.

Scenario 1 — Selecting the Right SDLC Model

The Situation: A financial services company is developing a high-transaction retail banking application. The development team wants to use Agile sprints to speed time to market, but security must meet strict PCI DSS compliance requirements.

The Managerial Response: The security manager should recommend integrating security directly into the Agile sprint cycles (DevSecOps). This involves: defining security requirements as product backlog stories, requiring that SAST and secrets scanners pass on every code commit as a "definition of done," and embedding a trained Security Champion within the development team to run first-line code reviews.

Scenario 2 — Remediating SQL injection flaws

The Situation: An application-layer penetration test identifies that a user-profile search field concatenates user inputs directly into query strings, creating a critical SQL injection vulnerability.

The Managerial Response: Although input filtering is a useful secondary defense, it is not a definitive fix. The development team must rewrite the query code to use Parameterized Queries (Prepared Statements). This ensures that user inputs are treated strictly as parameters, preventing the database engine from executing input data as commands.

Scenario 3 — Managing Open-Source Vulnerability Alerts

The Situation: A security manager receives an alert that a critical CVSS 9.8 remote code execution vulnerability (like Log4Shell) has been published against a popular open-source utility library used across multiple corporate applications.

The Managerial Response: Without a Software Bill of Materials (SBOM), the security team would be forced to manually audit all system files, losing valuable response time. If the team maintains a centralized SBOM database, they can query it to identify and patch affected applications within seconds. In the meantime, they should implement Web Application Firewall (WAF) rules as a compensating control.

Scenario 4 — Wiping Hardcoded Secrets from Repository History

The Situation: A developer accidentally commits a database connection string containing a plain-text password to a Git repository, and then deletes the secret in a subsequent commit.

The Managerial Response: Merely deleting the secret in the latest commit does not secure the system. Because Git maintains a complete, unencrypted history of all commits, any user with repository access can retrieve the password. The security manager must treat the credential as compromised and rotate the password immediately, and then configure pre-commit hooks to prevent future credential commits.

Domain 8 Summary: Software Development Security Essentials

Domain 8 focuses on integrating security requirements throughout the Software Development Lifecycle (SDLC). Building secure software relies on a proactive, "shift-left" approach: identifying threats during the design phase using STRIDE, implementing server-side input validation and parameterized queries to neutralize SQLi, and using context-aware output encoding to prevent XSS. Additionally, security teams must deploy SAST scanners inside repositories, use DAST to test running applications, and manage supply chain risks through Software Bill of Materials (SBOM) and Software Composition Analysis (SCA) dependencies. On the exam, remember that client-side validation is not a security control, and the data owner remains accountable for authorizing application access rights.

🎯 3 Key Exam Reminders

  • Server-Side Input Validation is Mandatory: Client-side input validation (using JavaScript) is a user experience control, not a security control. All security-significant validation must be executed on the server.
  • Symmetric and Asymmetric Hybrid: Software updaters use asymmetric cryptography to sign update packages with their private keys, and recipients verify the signature using the vendor's public key to confirm integrity.
  • Golden Ticket Vulnerability: Compromising the KRBTGT service account password hash allows attackers to forge Ticket-Granting Tickets (TGTs) indefinitely, requiring a sequence of two password resets to resolve.
